So here’s what this post is actually doing: tracing the theoretical and methodological lineage behind harness-coding practices. At each step along that lineage, a little more decision-making authority shifts from the human operator to the system under construction. The core claim I want to land is this—autonomy in coding agents (AI systems that generate, validate, and ship code with varying degrees of human oversight) is not a binary endpoint. It’s a spectrum. And I’m drawing on control theory, formal verification, and the philosophy of mind to argue that a well-designed agent harness (the orchestration layer that mediates between a large language model and the software development life cycle, or SDLC) can progressively internalize the decision-making functions that used to be exclusively human.

This post sits within a broader series where we build, layer by layer, a fully autonomous coding-agent harness. Each installment adds something: SDLC phase integration, security constraints, UI guardrails, spec-compliance checklists, failure-recovery policies. This one supplies the conceptual scaffolding those practical layers will rest on.

The Autonomy Spectrum: Five Levels of Delegation

Here’s the thing about calling a system “autonomous.” It’s either a threshold you pass or you don’t, right? Or so the marketing copy suggests. But a more useful framing is a continuum. Five levels capture the progression pretty well:

  • L1 — Syntax Translation. The model takes a human-specified instruction and spits out syntactically valid code. The human still chooses what to build, how to structure it, and whether the output is actually acceptable. Think of it as a typewriter with a thesaurus attached.
  • L2 — Local Validation. Now the system generates code and runs a scoped check—unit test, linter, type checker—before handing it back. Delegation extends to “is this locally correct?” but not to “is this the right thing to build?”
  • L3 — Task-Level Planning. You give it a task description, and it decomposes that into sub-tasks, picks tools, sequences operations, and iterates on partial failures. The human provides the goal and reviews the result. This is where most current coding agents—Cursor, GitHub Copilot Workspace, Devin—live in their standard configurations.
  • L4 — Project-Level Orchestration. The system manages a multi-file, multi-session project: it maintains a working hypothesis about architecture, coordinates with other agents or services, updates its own task graph in response to integration failures, and produces a reviewable diff with a justification narrative. The human is auditor, not director.
  • L5 — Self-Governing Architecture. The system ingests a product-level specification, determines which SDLC phases to execute, allocates its own compute budget, selects and composes its own verification strategies, and ships to a staging environment. The human’s role shrinks to setting the specification and adjudicating edge cases that the system flags as below its confidence threshold.

And here’s the critical observation that I keep coming back to: each transition is not a matter of “more of the same.” Moving from L2 to L3 requires a fundamentally different verification architecture—local type-checking simply cannot validate a multi-step plan. Moving from L4 to L5 requires the system to select its own verification strategies, which is a meta-cognitive act that no current production system performs reliably. At least, not without a human holding the leash.

A system that can’t verify its own architectural choices can’t be trusted at L4, no matter how fluent its code generation looks in a demo.

Theoretical Foundations

Control Theory and the Reference Signal

In classical control theory, a regulated system compares its output to a reference signal and adjusts its actuator to minimize the error (Åström & Murray, 2008). A human-directed coding agent is the analogue of an open-loop controller: the reference signal is the human’s instruction, and the “actuator” is the code-generation step.

But a system that generates its own reference signal can fail in ways an open-loop system simply can’t. The error signal becomes internal, and without an external comparator, drift accumulates silently. That’s the core risk of L4 and L5: the agent must maintain a meta-reference—a specification, a set of invariants, a cost function—against which it evaluates its own outputs. Ashby’s law of requisite variety (Ashby, 1956) formalizes the constraint: the controller’s internal model must be at least as complex as the system it regulates. For a coding agent, that means the harness’s verification apparatus must encode at least as much structural knowledge as the codebase it’s asked to modify. If the harness can’t simultaneously represent the dependency graph, the security policy, and the product specification, it can’t verify a self-generated plan at L4 or above. Period.

Formal Verification and the Proof-Design Coupling

Formal verification—the act of proving a program correct against a mathematical specification—is not merely a post-hoc test. In Hoare logic, the proof constrains the design space before implementation even begins (Hoare, 1969). A pre-condition, a post-condition, and an invariant together define the set of admissible implementations. The code is, in a sense, a witness to the proof rather than the other way around.

That inversion is precisely what an L5 harness would need to internalize. Instead of generating code and then checking it, the system would generate the specification constraints first, derive the admissible design space, and then synthesize an implementation that satisfies the constraints by construction. Verification isn’t a gate at that point; it is the generator.

Now, the boundary of what can be verified formally is, of course, finite. The halting problem (Minsky, 1937; Turing, 1936) is the canonical example: there exist program inputs for which no finite procedure can determine whether execution terminates. More broadly, McGinn (1989) argues that there may be problem classes in principle beyond the capacity of any finite verification process, though the halting problem remains the clearest and most practically relevant instance. For harness design, the implication is straightforward enough: L5 cannot be “fully verified” in a mathematical sense. It can only be bounded—its failure modes must be enumerable, and its confidence thresholds must be calibrated against a known distribution of past errors.

Philosophy of Mind: Functionalism and the Verification Gap

Is a coding agent at L5 genuinely “autonomous,” or is it just executing a very, very complex lookup? At bottom, that’s a question about the nature of agency itself. Functionalism (Putnam, 1967) holds that mental states are defined by their causal role in a system’s input-output mapping, not by the substrate that instantiates them. Under that view, a system that plans, verifies, and self-corrects in a manner functionally equivalent to a human engineer’s process qualifies as an agent—whether its “deliberation” runs on silicon or on a transformer’s attention weights.

However, the BDI (Beliefs, Desires, and Intentions) architecture of Rao and Georgeff (1991) introduces a stricter criterion: an intentional agent must maintain a persistent belief base, a set of goals (desires), and a committed plan (intention) that it updates in response to new information. A stateless LLM call doesn’t satisfy this. A harness that maintains a persistent project state, a goal hierarchy, and a revision log does approximate BDI intentionality, even if the underlying model has no persistent memory. And this distinction matters enormously for L4–L5 design: the harness, not the model, is the locus of agency.

Implications for Harness Design

So how does all this translate into actual design practice? A few principles follow.

Verification bounds autonomy. A harness that can’t verify a decision at level n shouldn’t delegate that decision to the model at level n. The harness’s verification capacity—not the model’s fluency—is the binding constraint. Design the verification pipeline first; the model’s role is to produce candidates within the space the verifier accepts.

The human-as-auditor role must be architecturally explicit. At L3 and above, the human doesn’t “approve code.” The human adjudicates exceptions: the system flags decisions below a confidence threshold, and the human resolves them. The harness must surface these exceptions in a structured, reviewable format—not as a wall of diff output, but as a decision log with justifications, alternatives considered, and the specific invariant that triggered the flag.

SDLC phases are the natural decomposition axis. The software development life cycle—requirements, design, implementation, testing, deployment, maintenance—gives you the phase boundaries at which autonomy can be graduated. A harness might grant L4 autonomy over the testing phase (the system selects, runs, and interprets test suites) while retaining L2 autonomy over the design phase (the system proposes architectures but the human picks). This phase-wise grading is more practical and safer than slapping a uniform autonomy level across everything.

Common Mistakes in Harness Construction

The following failures recur across practitioner reports and post-mortems, and I’ve seen them all firsthand:

  1. Verification as afterthought. The harness generates code, runs it, and treats a green test suite as proof of correctness. In practice, this means a service that passes its unit tests but violates the API contract defined in the specification document—because the specification was never encoded as a machine-checkable constraint. The fix: encode specifications as executable invariants before generation begins.

  2. Confusing fluency with competence. A model that produces well-formatted, syntactically valid code is not thereby a competent engineer. In practice, a Devin-style agent writes a plausible-looking migration script that passes syntax checks but drops a column in production because it never inspected the schema dependency graph. The fix: the harness must enforce a “read-before-write” policy for any modification to shared state.

  3. Uniform autonomy across phases. Granting the same autonomy level to requirements analysis, code generation, and deployment. In practice, a system given L4 autonomy over deployment autonomously rolls back a feature flag that a product manager had intentionally set for a staged rollout, because the system’s cost function treated the flag as “stale configuration.” The fix: phase-specific autonomy ceilings, enforced by the harness, not by prompt engineering.

  4. No confidence-gated escalation. The system either acts or it doesn’t; there’s no “I’m 72% confident and would like a human to confirm” state. In practice, an agent at L3 rewrites an authentication module because it believes the existing implementation is suboptimal, but can’t articulate why its confidence is sufficient to override a security review that was completed two weeks prior. The fix: a mandatory confidence threshold below which the system must emit a structured escalation request rather than a diff.

Discussion

Two threads remain that the preceding sections haven’t fully pulled on.

First, L5 is asymptotic. The Ashby bound implies that as the complexity of the system under regulation grows—and it will, as codebases scale—the verification apparatus must grow at least as fast. In practice, this means L5 isn’t a destination you arrive at. It’s a regime: the harness must continuously expand its verification surface as the codebase evolves. A harness that was sufficient for a 50,000-line monolith is not sufficient for a 500,000-line microservice topology. Autonomy at L5 is therefore a maintenance activity, not a one-time architectural choice you make on day one and forget about.

Second, the multi-agent dimension complicates everything. When two L4 agents coordinate on a shared codebase, the effective system complexity exceeds either agent’s individual verification capacity. Russell and Norvig (2020) note that multi-agent systems introduce coordination overheads—communication, consistency, and negotiation costs—that are superlinear in the number of agents. A harness supporting multi-agent coordination must therefore verify not just each agent’s output in isolation but the joint output against a shared invariant set. And that’s a qualitatively different verification problem from single-agent L4. It remains an open design challenge, and I’d argue it’s the one most likely to bite people first in production.
